# Contributing

## Rules

- Open one issue for each change, and deliver it in one pull request.
- When you change a file in `src/<id>/` other than `README.md`, increase the `version` in `src/<id>/devcontainer-feature.json`. Use [semantic versioning](https://semver.org/). The release does not publish a version again, so it does not publish a change that has no higher version.
- Do not edit `src/<id>/README.md`. Run `npm run docs` and commit the README in the same pull request.
- Install packages from the Debian archive. Do not write a version pin into `install.sh`.
- Start a new Feature at version `1.0.0`. In the same pull request, add a row to the Features table of `README.md`. `test-pr.yaml` gets the Feature ids from the changed files in `src/` and `test/`, so it needs no edit.
- Make each `*.sh` file pass `shellcheck` at its default severity.
- Write `test/<id>/scenarios.json` as JSON with no comments, and use `debian:sid` as the image of a scenario. The scenario jobs of `test-pr.yaml` replace each `debian:sid` in the file with their base image.

The `Lint` workflow runs `shellcheck` on each tracked `*.sh` file. It also checks the version and the README of each changed Feature.

### Test scripts and shellcheck

The CLI copies `dev-container-features-test-lib` into the test container, so `shellcheck` cannot read it. In each test script, put the directive `# shellcheck source=/dev/null` on the line above `source dev-container-features-test-lib`:

```bash
#!/bin/bash
set -e

# shellcheck source=/dev/null
source dev-container-features-test-lib

check "version" podman --version

reportResults
```

Without the directive, `shellcheck` reports `SC1091` and the `Lint` workflow fails.

## Set up

Open the repository in its dev container, or install Node.js and Docker. Then install the Dev Containers CLI at the version of `package-lock.json`:

```sh
npm ci
```

## Test

```sh
# The test of the default options and the scenarios of one Feature
npx devcontainer features test -f <id> -i debian:sid

# Only the scenarios of one Feature. Without -i, the duplicate test runs on ubuntu:focal,
# the default image of the CLI, so skip it.
npx devcontainer features test -f <id> --skip-autogenerated --skip-duplicated

# Every Feature except podman-outside-podman in one container on debian:sid, then the
# scenarios in test/_global
npm test

# Only the scenarios in test/_global
npm run test:global

# The shell scripts
git ls-files -z '*.sh' | xargs -0r shellcheck

# The README of each Feature
npm run docs
```

The jobs of `test-pr.yaml` test on `debian:sid`, `debian:trixie` and `ubuntu:noble`, on linux/amd64 only. A scenario with `keepid` in its name also runs in the `podman-host` job of `test-pr.yaml`. That job gives the rootless Podman of the runner the name `docker`. The CLI then starts a container with a non-root remote user with `--userns=keep-id`. Every scenario also runs under Docker in the `test-scenarios` job.

podman-in-podman and podman-outside-podman cannot be in one container: the install of the second one stops. podman-outside-podman also needs the Podman API socket of a host engine, and the container does not start when the directory of the socket is missing. Thus `npm test` and the `test-together` job of `test-all.yaml` leave podman-outside-podman out, and the other jobs test it alone. Before its tests, each job runs `.github/scripts/start-podman-host.sh`, which starts the rootful and rootless Podman API services of the runner. To test podman-outside-podman on your computer, start the Podman API socket of your user (`systemctl --user start podman.socket`), then run `npx devcontainer features test -f podman-outside-podman -i debian:sid --skip-scenarios`. The scenarios mount the socket directories of the runner, `/run/podman` and `$XDG_RUNTIME_DIR/podman`.

Rootless Podman with `--userns=keep-id` starts the container as the host user. On a runner, the host user has uid 1001 and is not the remote user. Under Docker (the test and test-scenarios jobs), `devcontainer features test` gives a non-root remote user the uid of the user that runs the CLI, so a scenario that needs a fixed uid sets `"updateRemoteUserUID": false` (foreign_uid_proxy and keepid_direct do). keepid_direct expects the runner uid 1001, so on your computer run it only in the podman-host job. A keep-id scenario that needs the entrypoint of a Feature to run as root sets `"containerUser": "root"`.

## Workflows

| Workflow | Runs on | Does |
| --- | --- | --- |
| `lint.yaml` | each pull request, each push to `main` | shellcheck, the compare of the two copies of `scripts/podman-common.sh`, the README check and the version check (with `semver`) |
| `validate-metadata-files.yml` | each pull request | validates each `devcontainer-feature.json` against the schema |
| `test-pr.yaml` | each pull request | tests each Feature with a changed file in `src/<id>/` or `test/<id>/` on `debian:sid`, `debian:trixie` and `ubuntu:noble` |
| `test-all.yaml` | each push to `main`, each Monday, by hand | tests each Feature alone on `debian:sid`, then all Features except podman-outside-podman together in one container, and in a third job the scenarios in `test/_global` |
| `test-manual.yaml` | by hand | tests the given Features on the given base image |
| `release.yaml` | each push to `main` that changes `src/` | publishes the Features to GHCR, one run at a time |

Each workflow runs on `ubuntu-latest`. A workflow that uses the CLI installs it from `package-lock.json` with `npm ci`.

## Release

After the merge, `release.yaml` publishes each Feature with a new version to `ghcr.io/dan-petty/devcontainer-features/<id>`. It also adds the git tag `feature_<id>_<version>`. GHCR makes a new package private, so the owner makes each package public after its first release.

## Dependencies

Renovate updates the CLI and `semver` in `package.json` and `package-lock.json`, the actions in `.github/workflows/` and the image in `.devcontainer/devcontainer.json`. `.github/renovate.json` extends the shared preset of [devops-cli](https://github.com/dan-petty/devops-cli). The devops-cli image publishes several tags a day, so Renovate updates it only on Monday, also for a patch.
