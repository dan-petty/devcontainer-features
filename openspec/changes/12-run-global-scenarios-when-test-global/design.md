# Design

## Decisions

- **Extend the existing `dorny/paths-filter` step with a `global` filter and a `global` output, and gate the new job with its own `if`.**: The action is already pinned at `.github/workflows/test-pr.yaml:32:- uses: dorny/paths-filter@ceb8a2b8f2d89434be7ff52d3de7ec3738c5cc9d # v4.0.3`, so the change adds no dependency, and each job keeps its own condition, so the Feature jobs stay as they are.
- **Run `npm run test:global` in the new job, as the weekly global job does.**: The script at `package.json:12:"test:global": "devcontainer features test --global-scenarios-only",` holds the CLI arguments, so the two workflows cannot drift.
- **Set `timeout-minutes: 30` on the job and `timeout-minutes: 25` on the run step, the values of the weekly global job.**: Both jobs run the same command on the same runner, and `.github/workflows/test-all.yaml:100:timeout-minutes: 30` and `.github/workflows/test-all.yaml:111:timeout-minutes: 25` show the bounds that the command already has.
- **Copy the full-SHA checkout pin of the weekly global job into the new job.**: `.github/workflows/test-all.yaml:102:- uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7` holds the same SHA as `.github/workflows/test-pr.yaml:28:- uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7`, and zizmor reports `unpinned-uses` for a tag.
- **Keep the `features` filter over `test/**`, the ids step and the gates of the three Feature jobs as they are.**: A global scenario change sets that filter true and the ids step then writes `[]`, so the Feature jobs skip and the second Expected item of the issue holds without a change to those jobs.
- **Deliver the live proof of the Expected section as a `Pending a person:` bullet under `## Workflow follow-up`.**: `openspec/config.yaml:64:A check only a person can run is a plain bullet starting "Pending a person:".` names that form, and only a person can open a pull request that changes only the global scenario file and read the check of its run.
- **Update `CONTRIBUTING.md` in the same change.**: The row of the Workflows table at `CONTRIBUTING.md:77:tests each Feature with a changed file in` names only the Feature tests, so the new job makes the table incomplete.
- **Leave `README.md` unchanged.**: Its sentence at `README.md:41:runs the scenario, so the run fails when a change in` stays true, because the weekly run still runs the scenario every Monday; the change adds a run and removes none.
- **Give the plan no spec delta.**: `openspec/config.yaml:32:A change that alters no behavior a consumer observes (tests, CI workflows, documentation, a refactor that` holds the rule that this CI workflow and document change follows, and the change adds no `devops` command, option or message.

## Rejected alternatives

- **Gate the global run with `on.pull_request.paths` at the workflow level.**: `.github/workflows/test-pr.yaml:3:pull_request:` triggers the whole workflow, and the file holds four jobs, each with its own `if`, so a workflow-level filter would gate all four at once.
- **Run the global scenarios on every pull request.**: The second Expected item of #12 requires a Feature-only pull request to skip the job, and the proof comment of PR #11 records the local `npm run test:global` run at 4 min 47 s, so every pull request would wait about 5 minutes for it.
- **Compute the flag in a new shell step from the changed files.**: `.github/workflows/test-pr.yaml:24:pull-requests: read # dorny/paths-filter lists the changed files through the API` shows that the pinned action already lists the changed files, and a shell step would repeat that call.
- **Call `npx devcontainer features test --global-scenarios-only` directly in the workflow.**: `package.json:12:"test:global": "devcontainer features test --global-scenarios-only",` holds those arguments, so a copy in the workflow drifts when the script changes.
- **Pin `actions/checkout` by the tag v7.**: `.github/workflows/test-pr.yaml:28:- uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7` is the full SHA that the workflow uses, and zizmor reports `unpinned-uses` for a tag.
- **Give the new job 15 minutes on the job and 15 on the step.**: `.github/workflows/test-all.yaml:111:timeout-minutes: 25` bounds the same command in the weekly job, so 15 minutes gives a slow runner less headroom than the command already has.
- **Give the new job 60 minutes on the job and 50 on the step.**: `.github/workflows/test-all.yaml:100:timeout-minutes: 30` bounds the same command, so a hung job would hold a runner twice as long as the existing job allows.
- **Rely on the weekly `test-all.yaml` run for the global scenarios, as PR #11 did.**: `.github/workflows/test-all.yaml:8:- cron: "17 5 * * 1"` starts that run once a week, and the push to `main` also runs the global scenarios, so a broken global scenario passes the pull request checks and fails only after the merge.
- **Report the live proof only in the Feasibility section and plan no task for it.**: The Expected section asks for a passing test-global check on a pull request, and `openspec/config.yaml:64:A check only a person can run is a plain bullet starting "Pending a person:".` asks for that bullet in the tasks.

## Security

The new `test-global` job runs code of a pull request on a hosted runner, so one trust boundary is the checkout of the pull request head, plus the network that `npm ci` and the scenario use to pull public images. The job keeps the workflow permission `contents: read` of `.github/workflows/test-pr.yaml:6:contents: read # read the files of the pull request`, checks out with `persist-credentials: false`, and passes no secret, so the token of the run is not stored in the git config of the runner. A person must confirm in the diff of `.github/workflows/test-pr.yaml` that the new job adds no `secrets.*` expression, no `permissions:` block and no `pull_request_target` trigger. The group verify `uv run devops ci --check --only actionlint,zizmor` fails the group when an action is unpinned or a shell line interpolates pull request data (zizmor `unpinned-uses` and `template-injection`); no test asserts the absence of a secret, so the diff review of a person covers that rule.
